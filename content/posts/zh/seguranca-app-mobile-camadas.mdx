关于移动应用安全的讨论，几乎都从混淆开始，也停在那里。它是最容易启用的措施，最容易向
管理层演示的措施，同时也是保护力最弱的一个——因为混淆并不能阻止任何事，它只是提高成本。

把其余一切组织起来的那个前提并不让人舒服：**应用运行在敌对区域**。设备属于用户，二进制
可以被检视，流量花半小时就能被拦截，而应用知道的任何东西，有心的人都能查出来。有用的问题
不是「怎么把它藏起来」——而是「服务端需要自己验证什么」。

我会继续用前几篇文章里的拍卖应用作为例子。如果用户能让服务端相信他出了一次实际并未发生的
价，那么再多的混淆也无济于事。

## 混淆可以做，但先把手册写好

发布版本的混淆会破坏你在下一个凌晨最想要的那件事：读懂一份调用栈。被混淆的符号会把崩溃
报告变成一串地址。

必须成对出现的是这三件事：做混淆、把符号映射作为发布产物保存下来，并且**在需要之前就把
反混淆流程写下来**。不是写成泛泛的文档——而是一份手册，写清确切的命令、去哪里下载那个
版本的映射文件，以及当映射对不上（因为有人重新构建过）时该怎么办。

我是在第一次真正需要它之后才写下这份手册的。第二次只花了五分钟，而不是一个下午。

## R8 的 keep 规则需要写明理由

这里有一个会让 Flutter 开发者困惑的地方：**R8 不会碰你的 Dart 代码**。发布版本的 Dart 是
AOT 编译的，超出了它的作用范围。R8 缩减与压缩的是 Android 那一侧——插件、原生 SDK，以及
作为依赖引入的 Kotlin 与 Java 代码。这恰恰是问题令人意外的原因：那些代码不是你写的，你
自然不会去怀疑它。

而症状从来不是编译错误。它是线上的 `ClassNotFoundException`，只出现在发布构建里，只出现在
那一条流程上——因为 SDK 在运行时按名称解析类，而那个名称已经不存在了。

修复方式是一条 `keep` 规则，而陷阱在于规则文件会变成垃圾场：

```proguard
# 推送 SDK 通过类名实例化 handler：
# 缺少这条 keep，推送只会在发布构建中静默失效。
-keep class com.example.push.** { *; }
-keepclassmembers class * implements com.example.push.Handler { *; }
```

每一条没有注释的 `keep` 都是一个之后没人能撤销的决定，因为不会有哪位未来的同事敢删掉一行
「不知道为什么存在」的规则。那条注释不是文档——它是日后删除它的许可。

## 证书绑定容易做，也容易变成炸弹

通过 SPKI 做证书绑定，应用到 REST 客户端，同时也要应用到 WebSocket——这是人们容易漏掉的
部分，因为 socket 通常有自己的客户端，会逃过 HTTP 层的配置：

```dart
// 绑定的是公钥（SPKI），不是证书本身：
// 用同一个密钥轮换证书，不会让应用失联
final pins = <String>[
  'sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=', // 当前
  'sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=', // 备用
];
```

有两件事，决定了证书绑定是在保护你，还是在制造事故：

**备用 pin。** 如果你只绑定一个密钥，而它发生轮换，那么所有已安装的应用会同时失去与服务端
的连接，而修复需要一个新的商店版本——最好的情况也要好几天。

**负责人与告警。** 证书绑定是唯一一种**会把运维失误变成应用彻底不可用**的安全措施。所以它
需要一个具名的责任人，以及崩溃监控里的一个告警阈值：一旦证书校验失败超过某条线，要有人在
客服之前就知道。

把这些和实现一起写进文档，是我在这个主题上做过的最成熟的决定，而我做得太晚了。

## 设备证明：挑选路径，不要全量开启

混淆提高成本；而设备证明才真正回答「这个请求是否来自我的应用、来自一台未被篡改的设备」。
Android 的 Play Integrity 与 iOS 的 App Attest 会产生一个由服务端自行校验的 token——控制权
从客户端转移出去，而这正是关键。

大多数团队恰恰在这里做过了头。对所有请求都做证明会消耗延迟、配额与客服成本，而大部分路径
并不值得：

- **需要证明的：** 欺诈有利可图的操作——身份认证与支付。
- **不需要的：** 配置读取、目录与公开内容。一次配置 `GET` 并不是欺诈面，对它做证明只会为
  「应用打不开」增加一种新方式。

我最初的清单更长，后来做了删减——在意识到社交流程与第三方登录实质上只是配置读取之后，我把
它们移出了清单；也移出了那些服务端本来就已有控制的管理类操作。

还有一个只在旧设备上才会出现的兼容性细节：**App Attest 需要 iOS 14**。如果你的应用还支持
iOS 13，就必须定义一条降级路径——也就是明确决定：对一台无法完成证明的设备该怎么办。拦截？
还是允许但设置限额？这是产品决策，不是工程决策，而且必须有人签字。

## 用环境变量契约替代把文件移出版本控制

当你在被跟踪的文件里发现密钥时，第一反应是把这个文件从版本控制里移除。这感觉是对的，却
制造了两个问题：再也没人知道应用需要哪些变量，而每搭一套新环境都变成考古工作。

更有效的做法是把两件事分开：

- **纳入版本控制的契约。** 一个始终保持更新的示例文件，列出所有必需变量，值全部是假的。
  它是不会腐烂的文档，因为缺了它构建就会失败。
- **值放在仓库之外。** 真正的密钥存在 CI 的保管库里，以及每个人的本地环境中。

另外要记住：只要一个密钥曾经出现在某次提交里，它就永久性地泄露了。要轮换它，而不只是删除
它——git 历史不会忘事。我也不得不清理过一个泄露进**文档**里的密钥，而那正是没有人会去查看
的地方。

在此之上，App Check 能帮上一个相邻的问题：确认调用你的平台服务的确实是你的应用，而不是
某个拿着你的密钥的脚本。

## 你不申请的权限，就是不存在的攻击面

性价比最高的那项安全措施完全不涉及密码学：删掉你不用的东西。我把声明过的权限过了一遍，
发现了一个早已废弃的功能留下的图片与存储访问申请。

每一条被声明的权限都是攻击面、都是商店审核被拒的理由、也是隐私页面上的一行内容。而在 iOS
上，含糊的用途说明会直接被拒——把这些字符串写好，同时是安全工作和过审工作。

屏幕上的敏感内容同理：在展示用户财务数据的页面上，当系统提示截屏时隐藏内容，成本很低，
却能防住最常见的那种泄露——被转发到群聊里的那张截图。

## 如果重做，我会怎么改

我会先从服务端的那个问题开始。在列出后端必须自行验证的内容之前，我花了很多时间在客户端侧的
措施上——混淆、隐藏、加大难度。服务端那份清单很短，而它才是真正重要的：如果服务端信任客户端，
客户端上再多的层次也补不回来。

另外，每项措施上线的那一天，我都会为它指定负责人。证书绑定、设备证明与 App Check 都会随时间
失效，可能是因为密钥轮换，也可能是因为平台政策变化——而一项没有责任人的安全措施，是一笔到期
日未知的债务。
