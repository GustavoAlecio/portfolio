Live Activity 在 WWDC 上看起来很简单。你声明一个 struct，调用 `request()`，发一条推送，
锁屏就更新了。它在模拟器上第一次就能跑通，而麻烦恰恰从这里开始：几乎所有会出错的地方，
都要等到之后才暴露——在真机上，在真实数据乱序到达的时候。

我花了几个月构建实时追踪类的 Live Activity，这是一份「哪里坏了」的清单。我会用
**一个实时拍卖**作为贯穿全文的例子——不是因为它是我参与过的应用，而是因为它一次性
覆盖了所有困难的部分：可被延长的倒计时、用户在竞拍者中的排名、乱序到达的出价，以及
一张必须在 extension 里渲染出来的商品图。

如果你从未做过，配置、视图与推送的完整路径在[从零到真机](/zh/blog/live-activity-flutter-do-zero)。
接下来的内容，是那篇文章不会告诉你的。

## 你放进 content state 的东西，每一次推送都要付费

`ActivityAttributes` 与 `ContentState` 的划分看起来是组织问题，其实是成本问题。
attributes 在 `request()` 之后不可变；而 content state 会随**每一次**推送传输。

把商品标题放进 content state，于是每一次出价更新都要带上商品标题。这看起来无害，直到
payload 变大，你才发现 Live Activity 推送的体积预算相当紧张——而让不变的字段占据高频
更新的空间，是一种会在最糟糕的时刻找你算账的浪费：拍卖正在收尾，而这次更新是唯一重要
的事。

## 状态不完整会让画面冻结

这是最糟糕的一个。服务端发来一个不完整的 content state——少了一个字段，或者出现一个
意料之外的 `null`——Live Activity 就会直接**停止更新**。没有报错，没有崩溃，也不会消失。
它冻结在最后一个有效状态上，而用户会一直盯着一个已经被超越的出价。

修复分两部分。第一部分是承认 payload 是敌对区域，并在一个你确定存在的基线之上构建状态：

```swift
extension AuctionActivityAttributes.ContentState {
    func normalized() -> Self {
        // 缺失的字段退回到一个安全默认值，
        // 而不是让整次更新失效
        Self(
            currentBid: currentBid,
            bidCount: bidCount,
            myRank: myRank,
            phase: phase,
            closing: closing ?? .paused
        )
    }
}
```

第二部分是容错解码。一个 `enum` 收到它不认识的值会抛出异常，并把整次更新一起带走：

```swift
enum AuctionPhase: String, Codable {
    case scheduled, open, extended, finalCall, closed
    case unknown

    init(from decoder: Decoder) throws {
        let raw = try decoder.singleValueContainer().decode(String.self)
        // 后端新增的阶段，不应该让已经上架的应用崩掉
        self = AuctionPhase(rawValue: raw) ?? .unknown
    }
}
```

这就是通用原则：在 Live Activity 里，**优雅降级是强制的**。你没有会话，没有可见的重试，
也没有会来抱怨的用户。你只有一块屏幕，它要么是对的，要么在说谎。

## 小组件不会说应用的语言

如果用户在应用内选择了语言，widget extension 完全不知道这件事。它是另一个进程，有自己的
bundle 和自己的 locale 解析逻辑——它跟随的是系统语言，而不是你的设置。

可行的做法，是让应用把这个选择写进 App Group container 里的一个文件，小组件在格式化任何
内容之前先从那里读取：

```swift
let group = FileManager.default.containerURL(
    forSecurityApplicationGroupIdentifier: "group.com.example.auction"
)
```

这对所有文本内容都适用，对所有需要格式化的内容也适用——货币尤其如此。我是以错误的顺序
发现这件事的：逐个场景去翻译，以为是文案问题，直到意识到那其实是架构问题。

## token 存在竞态

每一个 Live Activity 都会异步产生自己的 push token，而你需要把这个 token 连同 activity
的标识一起发给后端。这里有两个坑。

第一个是竞态：token 可能在注册流程结束之前就到达，也可能两个 token 几乎同时抵达。把这部分
状态的修改串行化到主线程，并**以 `activityId` 而不是拍卖 id 作为 replay 的键**，问题就解决
了——因为同一场拍卖在一天之内可能存在多个 activity。

第二个是：activity 的 token 并不能替代设备 token。两者你都需要——一个用来定位 Live
Activity，另一个用来识别另一端是哪个用户。

## 时钟不能依赖推送

让倒计时每秒通过推送更新是不可能的——系统会在几分钟内就开始限流。正确做法是让时钟
**在小组件内部**走动，而推送只负责校正锚点：

```swift
Text(timerInterval: state.closing.range, countsDown: true)
```

系统会免费为你完成这个动画，不消耗任何推送额度。推送要做的，只是在有人于最后几秒出价、
拍卖进入延长时告诉它「锚点变了」。最终得到的是一个连续的倒计时，即使几分钟内没有任何
更新到达，它依然是准确的。

有一个细节需要注意：如果后端没有把时钟标记为运行中，而拍卖显然还开着，你仍然必须把时间
显示出来。用户并不关心你的标志位。

## 只有在真机上才会浮现的细节

- **extension 里的图片不等于应用里的图片。** 在应用列表里加载流畅的图片，在 Live
  Activity 里未必能加载出来——extension 拥有不同的生命周期与资源预算。这需要在应用侧
  预先缓存，在 activity 需要它之前就写入 App Group。
- **Watch 会落到 `.small` family。** 它就是你已经当作「小尺寸情况」处理过的那套布局，
  而长标题正是在这里破坏整个构图。换行与自动缩放不是打磨，而是硬性要求。
- **用户名是不可预测的。** 事件行里放完整用户名会溢出；缩写是常态，不是例外。
- **结束也是生命周期的一部分。** 如果用户离开了页面，activity 就必须结束。否则它会在
  失去意义之后继续留在锁屏上——而僵尸 Live Activity 比没有更糟。
- **点击必须有去处。** 深度链接应该指向那个具体的商品，而不是首页。

## 如果重做，我会怎么改

我会从状态开始，而不是从 UI 开始。在拥有一个容错的数据模型之前，我花了不少时间调整锁屏
布局——而之后出现的每一个严重问题，都关于状态，而不关于构图。Live Activity 本质上是一个
同步问题，只是上面盖了一块很小的屏幕。

另外，我会先把文档写出来。为团队省下最多时间的并不是代码，而是一份说明后端、应用与小组件
之间契约的文档：每个字段代表什么，以及当它缺失时会发生什么。
